# 需求（2026-11-14 用户口述，Claude 复述后用户确认"复述对了"）

## 一句话

用户只说"原材料是什么、成品是什么"，AI 负责把中间的产线设计出来、验证跑通，再以一张看得见的流程图交给用户审。

## 用户确认过的需求

1. **入口是对话框**：后面接 Claude Code，也能换成别家大模型的命令行工具。
2. **用户只给两头**：输入和输出。中间分几站、每站怎么做，用户不管。
3. **AI 设计并检验**：由 AI 设计流程，并且自己验证它能跑通，不是画完就交。
4. **结果必须可视化**：流程长什么样要能看见，看不见用户就没法提意见。
5. **不受 n8n 的限制**：是自己的系统，不在 n8n 上搭。具体指哪些限制见下一节。
6. **流程要能反复跑**：设计完不是一张图，是一条以后每次投料都能出货的线。
7. **给用户自己用**：不卖、不给别人用。
8. **图支持手动改**：但大部分时间是用户提意见，AI 来改。
   - （2026-11-14 用户定）改图要支持鼠标拖；点节点要显示节点的信息和操作。"只能提意见让 AI 改或改文本文件"不接受。
   - 后果：conductor 自带的图不够用（只在运行期间存在，拖动不改流程，面板里没有本站规格和门标准），要有一块我们自己的画布页面。
   - （2026-11-14 用户定）"拖"分两步做。第一版：拖动摆放节点、点节点看信息和做操作、在节点面板里改本站规格和门的标准。第二版：拖线改走向、增删站。
   - （2026-11-14 用户定）点节点后的面板四类都要：**看这一站**（本站规格、门的合格标准、这件活在本站的半成品文件、退回次数和理由）；**验收与重跑**（人判门表态并写理由、重跑这一站、从这一站接着跑）；**直接改**（改规格和门标准，保存写回文件）；**让 AI 改**（对着这一站输入一句意见，交给 Claude Code 改，改完自动试跑）。
   - 用户看着图会问的问题，界面按这个顺序安排：这条线长什么样；我这件活在哪一站、卡住没有、为什么；有没有等我验收的；这一站干什么、合格标准是什么；这一站产出了什么；被退回几次、为什么；我觉得不对怎么改；改完生效了吗、跑通了吗。

## "n8n 的限制"指什么

这四条是 Claude 凭已有了解列的，2026-11-14 同行调研已逐条查证（读官方文档，未实测），详见 `docs/02-同行调研结论.md`：

1. 节点擅长调云端接口，碰本机的程序和文件很别扭。**属实，3.0 版起更严。**
2. 运行状态存在它自己的数据库里，不是文件，换工具或让 AI 接手都不方便。**运行状态属实；流程定义能导出成文本文件。**
3. AI 只是其中一种节点，不是流程的设计者；流程只有"下一步"，没有"验收、不合格退回"的概念。**前半句已过时（现在 AI 能替你搭和试跑）；后半句对一半（退回画得出来，但没有"门"）。**
4. 要养一个常驻服务（安装、升级、备份）。**属实，3.0 版起门槛更高。**

## 设计标准

用户级铁律第 5 条：工作流 = 成熟流程 + 文件化的半成品 + 每站一道门 + 一条退回路。搭之前过五条：先成熟再上线、半成品是文件、每站一道门（格式、谁判、合格标准）、退回路、退场。

用户搭一条线时要给三样：输入、输出、一份认可过的成品样例（或说清谁来判成品好坏）。

## Claude 的提议（用户还没点头）

第一版不做拖拽编辑器，只做三样：

1. 一份线定义文件的格式（站、门、退回路、退场），它是唯一真相。
2. 一个执行器：按定义逐站调命令行代理，过门，不合格退回。
3. 一个图页面：从定义文件生成，显示流程形状和每件货在哪站。

对话框先直接用 Claude Code 本身。这一版要验证的假设是：AI 设计的线，能不能第一次给人看时就已经跑通。成立之后再加手动改图（需求 8）和别家命令行（需求 1 的后半句）。

Claude 认为的差异点：站点是能碰本机的命令行代理；门是一等公民；先拿样例试跑通再给人看。

已知风险：对话生成流程这件事同行很多；Claude Code 官方可能自己加上同类功能。因为是自用，这两条只影响"值不值得自己做"，不影响能不能做。

同行调研后的修正（2026-11-14）：上面第 2 样"执行器"不一定要自己写。现成的 microsoft/conductor 已有门、退回、人工验收和流程图，要先动手对比再定。画图用 Mermaid（用纯文本描述、自动画成流程图的格式）即可，AI 能直接重写。

## 下一步

到 2026-11-15 为止已经做出来的：执行器（自己写，不用 conductor）、本机服务、画布页面、三条线。
其中"会议纪要线"和"技术文档翻译线"是 Claude 只拿两头和自己写的样例设计出来的。设计做法和踩到的坑记在 `docs/06-怎么从两头设计一条线.md`。

"这一版要验证的假设"（AI 设计的线，第一次给人看时就已经跑通）：**没有成立，至少没有按原话成立。** 两条线的第一版在一份样例上都 3 次全走通，但盲审者换了两件原料，会议纪要线两件都停线。补到三份样例、改了两轮之后，两条线才都做到 9/9。更准确的说法是：AI 设计的第一版只在它盯着的那份样例上跑得通；要用几份不一样的样例试跑并改上一两轮，才拿得出手。样例都是 Claude 自己写的，成品好坏也是 Claude 自己判的，用户还没看过。

1. 用户在画布上审这两条线（双击 `start-canvas.cmd`，左上角切换线）：看试跑的产出，批准或提意见。玩具线上还留着一条 AI 提的改动等用户采用或不要。
2. 用户拿一件自己的真实材料来：说两头、给一份样例。Claude 照 `docs/06` 设计，用户在画布上审。这是第一条真线。
3. 用户认可过成品之后，再决定要不要把"从两头设计一条线"固化成页面上的功能或 Claude Code 的技能（铁律第 5 条：手工做成两次且成品被认可，才上产线）。
4. 处理盲审挑出的问题，见 `docs/04-画布页面.md`。

**（2026-11-15 用户举的第一个真实例子）** 用一个人物的原画，生成他四个方向的站立、走动、跑步的像素画；方向可以是上下左右，也可以是仙剑奇侠传那种斜向；用户判断需要 ComfyUI。调研结论、草案和执行器要补的六样能力见 `docs/07-第一条真线-原画转像素动画.md`。这件事还没手工做成过，先手工做出一个方向的走路给用户看，再谈搭线。

没做的：原料或成品不是一段文字的线；需要工人动本机文件或跑命令的站；几站同时干；拖线改走向、增删站；换 Codex 当工人。
