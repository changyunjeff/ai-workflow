# 命令行代理生态：Claude Code 自带能力、别家命令行工具、社区编排器（截至 2026-11-14）

> 读法说明
> - 所有网页均在 **2026-11-14** 读取；这些工具按月甚至按周变，日期之后的变化不在本笔记内。
> - 每条事实后的标记：**【一手】**= 我读了官方文档 / 官方仓库 README / GitHub 官方接口原文；**【二手】**= 来自第三方文章或搜索摘要；**【未核实】**= 没找到可靠出处，或只凭记忆，不能当事实用。
> - 术语：**命令行代理**（CLI agent）= 在终端里运行、能自己读写文件和跑命令的大模型工具，如 Claude Code、Codex CLI。**无头模式**（headless / non-interactive）= 不开聊天界面，一条命令进、结果出，适合被脚本调用。**工位**= 产线上的一站。**门**= 一站做完后的验收检查。**退回**= 验收不过时把活送回前面某一站。**子代理**（subagent）= 主对话派出去干一件小事的独立 Claude，带自己的上下文。
> - 八条需求编号沿用任务书：1 对话框入口且可换厂商；2 用户只给两头；3 AI 设计并自证跑通；4 可视化（形状＋每件活在哪）；5 不受 n8n 那几条限制（本地程序/文件顺手、状态在文件、AI 是设计者、有门和退回、不用常驻服务）；6 可反复投料；7 个人自用；8 图可手改。
> - 评分记号：**满**= 满足；**半**= 部分满足；**否**= 不满足；**？**= 未能核实。

## 一、Claude Code 的"工作流脚本"到底是什么？它卡在哪条需求上？

### Takeaway
官方名叫 **dynamic workflows（动态工作流）**：Claude 按你的描述写一段 JavaScript 脚本，由运行时在后台调度几十到几百个子代理；脚本可存成 `/名字` 命令、带参数反复跑，有 `/workflows` 进度视图，但**没有流程形状图、不能在图上改、状态默认在脚本变量和会话目录里而不是固定位置的带状态文件、运行中不能停下来等人验收、工位只能是 Claude**。也就是说它天然满足需求 2、6、7，半满足 1、3、5，不满足 4（形状图）和 8。

### Cited Findings

**它是什么、怎么得到**
- 【一手】定义："A dynamic workflow is a JavaScript script that orchestrates many subagents at once. Claude writes the script for the task you describe, and a runtime executes it in the background while your session stays responsive." — [Claude Code 文档：workflows](https://code.claude.com/docs/en/workflows.md)
- 【一手】与子代理 / skills / agent teams 的本质区别是"谁拿着计划"：工作流是"A script the runtime executes"，下一步由脚本决定，中间结果在"Script variables"，可重复的是"The orchestration itself"，规模"Dozens to hundreds of agents per run"。 — [workflows 文档对比表](https://code.claude.com/docs/en/workflows.md#when-to-use-a-workflow)
- 【一手】可用范围："available on all paid plans, with Anthropic API access, and on Amazon Bedrock, Google Cloud's Agent Platform, and Microsoft Foundry. On Pro, turn them on from the Dynamic workflows row in `/config`." 可用界面：CLI、Desktop 应用、IDE 扩展、`claude -p`、Agent SDK。 — [workflows 文档](https://code.claude.com/docs/en/workflows.md#turn-workflows-off)
- 【一手】官方博客（发布日期 2026-05-28）称已正式发布："Dynamic workflows are generally available in the Claude Code CLI"（另含 Desktop、VS Code 扩展）。 — [Anthropic 博客](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code)；【二手】有第三方文章仍写"research preview、需 v2.1.154+"，与博客的"正式发布"说法不一致，以官方博客和文档为准。 — [第三方摘要（搜索结果）](https://agentic-ai.readthedocs.io/en/latest/WorkflowBuilders/dynamic-workflows/)
- 【一手】触发方式：在提示里说"use a workflow"或写关键词 `ultracode`；或 `/effort ultracode` 让整场会话每件大活都自动走工作流；或直接运行已有命令（自带 `/deep-research`，或自己存的）。 — [workflows 文档](https://code.claude.com/docs/en/workflows.md#have-claude-write-a-workflow)

**脚本格式与接口**
- 【一手】文件首句必须是 `export const meta = {...}`，且是纯字面量（`name`、`description` 必填，可选 `phases`）；正文是普通 JavaScript（不是 TypeScript），可直接顶层 `await`。 — [workflows 文档：Edit a saved script](https://code.claude.com/docs/en/workflows.md#edit-a-saved-script)
- 【一手】正文可用的函数：`agent()`（派一个子代理）、`pipeline()`（每个条目独立走完各阶段）、`parallel()`（同时跑并等齐）、`phase()`（在进度视图里分组）、`log()`、全局变量 `args`（调用时传入的输入）。 — [workflows 文档](https://code.claude.com/docs/en/workflows.md#what-the-saved-script-looks-like)
- 【一手】`agent()` 可带 `schema`（JSON Schema，强制子代理返回结构化结果）；校验失败最多重试 5 次（`MAX_STRUCTURED_OUTPUT_RETRIES` 可调）；还可带 `stallMs`（单个代理的"无输出超时"）。 — [workflows 文档](https://code.claude.com/docs/en/workflows.md#what-the-saved-script-looks-like)
- 【一手】随 Claude Code 分发的内置参考（`/workflow-authoring` skill，本机 2026-11-14 加载原文）另列出：`agent()` 的可选项 `label / phase / model / effort / isolation:'worktree' / agentType`（`agentType` 可指定 `.claude/agents` 里的自定义子代理）；`budget`（本轮 token 预算，`budget.total / spent() / remaining()`，用户用"+500k"这类指令设上限后是硬上限）；`workflow(名字或{scriptPath}, args)`（把另一条工作流当子步骤跑，只能嵌一层）。 — [官方文档对该 skill 的说明](https://code.claude.com/docs/en/workflows.md#edit-a-saved-script)（skill 正文为本机文件，无公开网址）
- 【一手】脚本里 `Date.now()`、`Math.random()`、无参 `new Date()` 会直接抛错（为了让重跑可复现）；时间戳要经 `args` 传入。 — [workflows 文档](https://code.claude.com/docs/en/workflows.md#edit-a-saved-script)

**存在哪、怎么带新输入重跑**
- 【一手】在 `/workflows` 里选中一次运行按 `s` 保存，两个位置二选一：项目内 `.claude/workflows/`（随仓库共享）或个人 `~/.claude/workflows/`；之后以 `/<name>` 运行；同名时项目的优先。也可放进插件的 `workflows/` 目录分发。 — [workflows 文档：Save the workflow for reuse](https://code.claude.com/docs/en/workflows.md#save-the-workflow-for-reuse)
- 【一手】没保存的那次运行，脚本也会落盘："Claude Code writes the run's script to a file under your session's directory in `~/.claude/projects/`"，可打开看、对比、改完让 Claude 从改后的版本重跑。 — [workflows 文档：How a workflow runs](https://code.claude.com/docs/en/workflows.md#how-a-workflow-runs)
- 【一手】带新输入重跑靠 `args`："A saved workflow can accept input through the `args` parameter... Use this to supply a research question, a list of target paths, or a configuration object at invocation time instead of editing the script for each run."例：`Run /triage-issues on issues 1024, 1025, and 1030`。 — [workflows 文档：Pass input](https://code.claude.com/docs/en/workflows.md#pass-input-to-a-saved-workflow)
- 【一手】改了保存的脚本后，用 `/reload-skills` 重新读入，再跑 `/<name>`。 — [workflows 文档](https://code.claude.com/docs/en/workflows.md#edit-a-saved-script)

**续跑（resume）语义**
- 【一手】续跑按"代理启动顺序"回放：已完成的代理直接返回存下的结果；从**第一个提示词有变化的代理起，它和它之后的全部重跑**（包括已完成的）；失败的代理及其之后启动的全部重跑；停止时还在跑的从头来。 — [workflows 文档：Which agents run again](https://code.claude.com/docs/en/workflows.md#which-agents-run-again)
- 【一手】续跑绑定在**同一个会话**上：退出 Claude Code 后运行不会自己继续；要 `claude --resume` 回到那个会话再让 Claude 重新发起；"In a fresh session, Claude has no earlier run to relaunch and starts the workflow over."找不到存档时报 `nothing to resume`，不会自动重头跑。 — [workflows 文档：Resume after you leave the session](https://code.claude.com/docs/en/workflows.md#resume-after-you-leave-the-session)
- 【一手】运行存档放在会话目录（`~/.claude/projects/` 下）；内置参考说该目录里有 `journal.jsonl`，记录每个代理的真实返回值。 — [workflows 文档](https://code.claude.com/docs/en/workflows.md#resume-after-you-leave-the-session)（`journal.jsonl` 一名出自本机内置 skill 原文）
- 【一手】撞到订阅用量上限时，交互式终端会话和 Desktop 本地会话里运行会暂停、等额度恢复后自己继续（最多等两次、24 小时内恢复才等）；`claude -p`、Agent SDK、后台会话、定时任务会话里**不暂停，直接失败**。 — [workflows 文档：usage limit](https://code.claude.com/docs/en/workflows.md#when-a-run-hits-your-usage-limit)

**数量与花费上限**
- 【一手】默认最多 16 个代理同时跑（CPU 少则更少；`CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS` 可设 1–256，需 v2.1.269+）；单次 `parallel()`/`pipeline()` 最多 4,096 个条目；**每次运行总共最多 1,000 个代理**。 — [workflows 文档：Behavior and limits](https://code.claude.com/docs/en/workflows.md#behavior-and-limits)
- 【一手】超过 25 个代理或预计超过 150 万 token 时，任务栏显示 `Large workflow` 警告，但"The warning is advisory: it doesn't pause or limit the run."另有"规模建议"设置 `workflowSizeGuideline`（small <5、medium <10、large <50 个代理；默认 medium，Pro 套餐默认 small），是建议不是硬限。 — [workflows 文档：Cost](https://code.claude.com/docs/en/workflows.md#cost)
- 【一手】无头运行可用 `--max-budget-usd` 封顶，到顶即停掉后台工作。 — [headless 文档](https://code.claude.com/docs/en/headless.md#background-tasks-at-exit)

**进度怎么看、有没有图**
- 【一手】`/workflows` 列出运行中和已完成的工作流；进度视图"shows each phase with its agent counts"，可逐层点进某阶段、某代理，看它的提示词、最近的工具调用和结果；按键：`p` 暂停/继续、`x` 停止、`r` 重启选中代理、`s` 保存为命令。输入框下方任务栏还有一行进度摘要。 — [workflows 文档：Watch the run](https://code.claude.com/docs/en/workflows.md#watch-the-run)
- 【一手】Desktop 应用里：审批卡片显示工作流名、阶段清单和 token 提醒；"The progress view appears in the Background tasks side pane." — [workflows 文档](https://code.claude.com/docs/en/workflows.md#approve-the-plan-before-it-runs)
- 【一手】整篇 workflows 文档、官方博客、文档总索引里都没有出现流程图 / 节点连线图 / 看板这类视图；能看到的"形状"只有阶段清单（`meta.phases`）和按阶段分组的代理树。 — [workflows 文档](https://code.claude.com/docs/en/workflows.md)；[官方博客](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code)；[文档索引 llms.txt](https://code.claude.com/docs/llms.txt)

**门、机器验收、退回**
- 【一手】循环和分支写在脚本里，官方示例就是"跑检查→修→再跑，直到通过或连续两轮没进展"：`use a workflow to run npx tsc --noEmit and keep fixing the reported errors until the type check passes or two rounds in a row make no progress`。 — [workflows 文档：Example prompts](https://code.claude.com/docs/en/workflows.md#keep-fixing-until-a-check-passes)
- 【一手】但脚本本身碰不到文件和命令行："No direct filesystem or shell access from the workflow itself — Agents read, write, and run commands. The script coordinates the agents"；也不能 `import()` 任何库。 — [workflows 文档：Behavior and limits](https://code.claude.com/docs/en/workflows.md#behavior-and-limits)
- 【一手】**运行中不能等人**："No mid-run user input — A run pauses on its own only for agent permission prompts and a usage-limit wait. For sign-off between stages, run each stage as its own workflow"。 — [workflows 文档：Behavior and limits](https://code.claude.com/docs/en/workflows.md#behavior-and-limits)

**非 Claude 的命令行工具能不能当一站**
- 【一手】官方原话："In every approach the workers are Claude sessions. To involve a different tool, expose it to Claude as an MCP server."（MCP = 让 Claude 调用外部工具的标准接口） — [Claude Code 文档：Run agents in parallel](https://code.claude.com/docs/en/agents.md)

**无头调用与权限**
- 【一手】`claude -p` 和 Agent SDK 里工作流不弹审批框，走普通权限判定；可用允许规则 `Workflow`（放行全部）或 `Workflow(<name>)`（放行某条已保存的）。 — [workflows 文档](https://code.claude.com/docs/en/workflows.md#approve-the-plan-before-it-runs)
- 【一手】关键词 `ultracode` 在 `-p`、定时任务、webhook 里**不触发**工作流；但 `-p` 模式下"User-invoked skills and custom commands work. Include `/skill-name` in the prompt string"。 — [workflows 文档](https://code.claude.com/docs/en/workflows.md#where-the-keyword-works)；[headless 文档](https://code.claude.com/docs/en/headless.md#create-a-commit)
- 【一手】`claude -p` 结束时会等后台工作流，但默认最多空等 10 分钟就丢弃未完成结果（`CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` 可调，设 0 为不限）。 — [headless 文档：Background tasks at exit](https://code.claude.com/docs/en/headless.md#background-tasks-at-exit)

**Claude Code 其余原生积木（与产线有关的部分）**
- 【一手】并行干活共五种方式：subagents、agent view（`claude agents` 一屏看所有后台会话，**research preview**）、agent teams（带共享任务清单和互发消息，**experimental 且默认关闭**）、Projects（云端长期对话，**public beta**）、dynamic workflows。 — [agents 文档](https://code.claude.com/docs/en/agents.md)
- 【一手】无头模式：`claude -p "<提示>"`；`--output-format text|json|stream-json`；`--json-schema` 强制结构化输出（结果在 `structured_output` 字段）；成功退出码 0、失败非 0、被 SIGTERM 终止为 143；权限用 `--allowedTools`、`--permission-mode`（如 `acceptEdits`、`auto`、`dontAsk`）、`--permission-prompts none`（v2.1.259+，没人值守时把要问人的一律拒绝）；`--continue` / `--resume <会话ID>` 续接对话；`--bare` 跳过钩子、skills、插件、MCP、CLAUDE.md（官方称将成为 `-p` 的默认）；JSON 输出含 `total_cost_usd`。 — [headless 文档](https://code.claude.com/docs/en/headless.md)
- 【一手】定时任务三种：云端（原名 routines，可按时间、API 调用、GitHub 事件触发，但拿不到本地文件）、Desktop 本地（能读本地文件，但"only fires while the app is open and your computer is awake"；任务提示词存成 `~/.claude/scheduled-tasks/<task-name>/SKILL.md`；有"Manual"档＝存一条提示词随点随跑）、会话内 `/loop`。 — [Desktop scheduled tasks 文档](https://code.claude.com/docs/en/desktop-scheduled-tasks.md)
- 【一手】`/goal`：设一个完成条件，Claude 一直干到满足为止。 — [文档索引](https://code.claude.com/docs/llms.txt)
- 【一手】Desktop 的 Code 标签页是可拼装的面板："chat, diff, browser, terminal, file, plan, tasks, and subagent"；tasks 面板显示"subagents, background shell commands, and dynamic workflows"；本地会话里"click an HTML, PDF, or video path in the chat to open it in the Browser pane"，但这种预览"doesn't load anything from the web"。 — [Desktop 文档](https://code.claude.com/docs/en/desktop.md)
- 【一手】**mods**（改 Claude Code 自己界面的插件，v2.1.287+ / Desktop v2.1.286+ 默认开启）：能在对话旁画一个常驻面板（pane），可加命令、定时器、读写文件、调模型。面板元素里有 `Svg`："a `source` of SVG markup up to 131,072 characters"，仅 Desktop 和 VS Code 支持；终端里只能用字符格子（`Raster`）。可用 `$.clock.every` 定时重画，`$.store` 跨会话存值。WSL 会话里插件不可用；`claude -p` 里钩子会跑但不画界面。 — [mods 概览](https://code.claude.com/docs/en/plugins/mods/overview.md)；[mods 界面](https://code.claude.com/docs/en/plugins/mods/interface.md)；[mods 参考](https://code.claude.com/docs/en/plugins/mods/reference.md)
- 【一手】Artifacts："turn Claude Code's work into live, interactive pages on claude.ai"，可私有或分享。 — [文档索引](https://code.claude.com/docs/llms.txt)
- 【一手】最新版本：变更日志顶部是 2.1.325（2026-11-13）；近三个版本里与工作流有关的条目都是行为修补（暂停/停止的通知、Desktop 撞额度后暂停续跑等）。 — [Claude Code changelog](https://code.claude.com/docs/en/changelog.md)

**对八条需求的评分（只用原生工作流，不加任何外层）**

| 需求 | 评分 | 依据（均见上文一手出处） |
|---|---|---|
| 1 对话框入口、可换厂商 | 半 | 入口就是 Claude Code 对话框；但"workers are Claude sessions"，别家只能经 MCP 接进来 |
| 2 只给两头 | 满 | "Claude writes the script for the task you describe" |
| 3 设计并自证跑通 | 半 | 能写完就跑、能循环到检查通过；但没有"先试跑验证、通过才交付"的内建环节 |
| 4 可视化 | 半偏否 | 有阶段＋代理数的进度树，可点进看每个代理；没有流程形状图，也没有"每件活在哪一站"的视图 |
| 5 不受 n8n 限制 | 半 | 本地程序/文件顺手（代理自己跑命令）、无常驻服务、AI 是设计者——满；但状态默认在脚本变量和会话目录，不是固定位置带状态的文件；门和退回要自己写进脚本；运行中不能停下等人 |
| 6 可反复投料 | 满 | 存成 `/名字`，用 `args` 传新输入 |
| 7 个人自用 | 满 | 本机运行，所有付费套餐可用 |
| 8 图可手改 | 否 | 没有图；能手改的是 `.js` 脚本本身 |

### Inferences
- 用户的设计标准里"任何一站都能交给只拿到半成品和本站规格的全新代理"与工作流的 `agent()` 天然吻合（每个 `agent()` 就是全新上下文）；但"半成品是固定位置带状态的文件"必须靠约定——让每个代理按路径读写文件，脚本只传路径不传内容。
- "机器判的门"在原生工作流里其实是"一个 Claude 代理去跑检查命令，再用 `schema` 把通过与否报回来"，中间隔了一层模型；`schema` 校验本身是机器强制的，但命令结果的转述不是。想要完全不经模型的机器门，得在工作流之外放一个薄的运行器（见第五节）。
- "人判的门"与"运行中不能等人"冲突，官方给的出路是把一条线在人审处切成几条工作流——这等于要一个外层来记"这件活停在哪条线的哪一站"，正好就是状态文件该干的事。
- 续跑缓存按"代理启动顺序＋提示词是否变化"判定，且绑定会话；所以它适合"同一次运行中断后接着跑"，不适合当作产线的长期状态存储。跨天、跨会话的进度必须自己落文件。
- 已保存的工作流既然"become commands"，而 `-p` 支持在提示词里写 `/命令名`，推断可以用 `claude -p "/线名 输入" --allowedTools "Workflow(线名)"` 无人值守地投料；**本次没有实测**，且要注意 10 分钟空等上限和撞额度直接失败这两条。

### Inferences
- "方法论包"和"会话看板"两类解决的是软件开发这一种固定的线，或者只管并行会话，不回答"用户只给两头、AI 设计任意产线"；可以排除出候选，但其中的做法值得借：Spec Kit 的结论分级（verified / partial / failed）、ccpm 的"本地文件先行、再显式同步"、agent-orchestrator 的"按状态分道、把需要人的排最上面"。
- 最接近用户设计标准的是 babysitter（流程即代码、门强制、状态文件、可续跑）和 Archon（门＋循环到命令通过＋人工审批＋多厂商）。两者都缺"AI 从两头自己设计"的明确承诺和"可编辑的图"；Archon 还把状态放进数据库，正好撞上用户不要的那条。
- "图"这件事上只有两个项目真正有：microsoft/conductor（运行时的实时图，只读）和 CC Workflow Studio（设计时的可编辑图，不管运行）。两者合起来才是需求 4＋8，而它们互不相通，且前者不能把 Claude Code / Codex 命令行当正式工位。
- 没有任何一个项目把"图上显示每件活停在哪一站"和"可自定义的多站产线"放在一起；看板类项目有前者，引擎类项目有后者。这是整个生态里最明显的空档。
- Windows 是普遍的弱项：多数 README 不提；依赖 tmux（Claude Squad）、Docker（OpenHands）、Go＋bun＋opencode（sgai）的项目在 Windows 11 上落地成本高。有明确 PowerShell 安装路径的只有 Archon、microsoft/conductor、ruflo、Spec Kit（声明支持 Windows）、agent-orchestrator 和 Aperant（有安装包）。
- 星数不等于合用：星数最高的几个（Spec Kit、ruflo、BMAD）恰恰离"AI 设计任意产线"最远；最对路的 babysitter、conductor 只有几百到一两千星，长期维护风险要自己掂量。

## 五、总体：哪个现成方案或组合最接近？最大的缺口是什么？如果答案是"Claude Code 工作流脚本＋生成的图"，上面那层薄层到底要补什么？

### Takeaway
最接近的现成底座是 **Claude Code 自带的动态工作流**（已满足"对话入口、只给两头、可反复投料、个人自用、本地文件顺手、无常驻服务"），外部项目里没有哪个整体上更接近；最大的缺口是**"一份既是规格又是图的产线定义"**——现有工具要么有可跑的线没有图，要么有图没有门、状态和每件活的位置——以及**"交付前自证跑通"**。薄层要补七样东西，其中有一个需要先拍板的岔路：门和状态由工作流脚本里的代理来做，还是由一个外部小运行器来做。

### Cited Findings
- 【一手】原生工作流已覆盖的部分：Claude 按描述写脚本；存为 `/名字`、用 `args` 投新料；循环到检查通过；代理能读写本地文件、跑本地命令；本机后台运行、无需服务。 — [workflows 文档](https://code.claude.com/docs/en/workflows.md)
- 【一手】原生工作流明确做不到的部分：脚本自己不能读写文件或跑命令；运行中不能等人签字（"For sign-off between stages, run each stage as its own workflow"）；工位只能是 Claude 会话（别家走 MCP）；续跑绑定会话；没有流程图视图。 — [workflows 文档：Behavior and limits](https://code.claude.com/docs/en/workflows.md#behavior-and-limits)；[agents 文档](https://code.claude.com/docs/en/agents.md)
- 【一手】可借来显示图的官方面板：Desktop 浏览器面板点开本地 HTML（不加载外网资源）；mods 面板的 `Svg` 元素（≤131,072 字符；Desktop / VS Code；可用 `$.clock.every` 定时重画；mods 能读写文件）；Artifacts。 — [Desktop 文档](https://code.claude.com/docs/en/desktop.md)；[mods 参考](https://code.claude.com/docs/en/plugins/mods/reference.md)；[mods 界面](https://code.claude.com/docs/en/plugins/mods/interface.md)
- 【一手】外部最接近的四个各缺一块：Archon（有门、循环到命令通过、人工审批、Claude Code＋Codex，但状态在 SQLite、线要手写 YAML）；microsoft/conductor（有实时流程图、门、按退出码路由，但 Claude Code 只是实验性接入）；CC Workflow Studio（有可编辑画布和 AI 改图、可导出到多家，但 README 未见门、状态、运行位置）；babysitter（流程即代码、门强制、状态是文件、可续跑，但没有流程形状图，流程要写 JS）。 — [Archon](https://raw.githubusercontent.com/coleam00/Archon/main/README.md)；[conductor](https://raw.githubusercontent.com/microsoft/conductor/main/README.md)；[cc-wf-studio](https://raw.githubusercontent.com/breaking-brake/cc-wf-studio/main/README.md)；[babysitter](https://raw.githubusercontent.com/a5c-ai/babysitter/main/README.md)
- 【一手】各家命令行都能被一行命令非交互调用并返回 JSON（见第三节表格），所以"可换厂商"在技术上是命令模板问题。 — [Claude headless](https://code.claude.com/docs/en/headless.md)；[Codex](https://learn.chatgpt.com/docs/non-interactive-mode)；[Gemini](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/headless.md)；[Cursor](https://cursor.com/docs/cli/headless)；[Goose](https://raw.githubusercontent.com/aaif-goose/goose/main/documentation/docs/guides/goose-cli-commands.md)

### Inferences

**为什么不直接采用某个外部项目**
- Archon 和 conductor 都把"线"交给人写 YAML，AI 只是节点或辅助——正是用户列为 n8n 限制的"AI 只是节点不是设计者"。CC Workflow Studio 解决了图，但不管门、状态和运行。babysitter 最合设计标准，但没有图，且对 Claude Code 之外的外壳多为实验性。把其中任何一个改到满足八条，工作量不小于在原生工作流上加薄层，还多背一份别人的维护节奏。
- 反过来，这些项目是很好的参照物：babysitter 的"门是强制的、日志不可改、可从任一点续跑"，Archon 的 `until_bash`（由命令结果判定循环何时结束）和 `fresh_context`（每轮换全新代理），conductor 的"路由由规则决定、不由模型选下一步"和实时流程图，Goose 配方的"检查命令失败→执行补救→清空对话重来"。

**最大的缺口**
1. **一份"产线规格文件"同时驱动脚本和图。** 现在的原生工作流里，线的定义就是那段 JS；图无从生成，手改图也无处落地。需要一个中间层：站、每站的输入输出文件位置、门（格式、谁判、合格标准）、退回到哪一站、退场条件——全写在一个文件里，脚本和图都从它生成。这样"图可手改"才有意义（改图＝改规格文件）。
2. **交付前自证跑通。** 生态里没有任何工具把"拿样例原料完整跑一遍、每道门都真的判过、成品真的落地，然后才交给用户审"做成固定环节；现有的都是"写完就跑"或"校验语法"。
3. **每件活在哪一站。** 引擎类工具显示"一次运行走到哪个节点"，看板类工具显示"每张任务卡在哪一道"，没有把两者合在可自定义的线上的。只要状态是文件，这一条其实很便宜：图读状态文件即可。

**薄层必须补的七样东西**
1. **产线规格文件**（固定位置，例如每条线一个目录）：站的清单；每站的规格（给全新代理看的那份说明）、输入文件位置、输出文件位置；每道门的格式要求、判定者（机器或人）、合格标准；不合格退回哪一站、最多退几次；整条线的退场条件。
2. **状态文件**：每件活一个，记录当前站、状态（进行中 / 待验收 / 待人审 / 退回 / 完成）、第几次尝试、各站产物的路径。注意脚本里取不到当前时间（`Date.now()` 会抛错），时间戳要由代理或外层写入。
3. **规格→可运行物的生成器**：把规格文件变成能跑的东西（见下面的岔路）。每站只传"规格＋文件路径"，不传对话内容，保证任何一站都能交给全新代理。
4. **门的执行**：机器门＝跑一条检查命令并看产出文件；人审门＝把状态置为"待人审"并停下，用户表态后再续。因为原生工作流运行中不能等人，人审门处必须把线切段，或者交给外层运行器。
5. **试跑验证环节**：设计完先用样例原料跑通全线，把"每道门的判定结果＋成品位置"写成一份验证记录文件；记录齐全才向用户出示图。
6. **图页面**：由规格文件＋状态文件生成，显示线的形状、每道门的要求、退回箭头、每件活当前所在的站。显示载体三选一：本地 HTML（Desktop 浏览器面板直接点开，但必须自带全部样式和脚本，不能引外网资源）；mods 面板里的 SVG（常驻对话旁、可定时刷新，仅 Desktop / VS Code，且单张图上限约 13 万字符）；Artifact 页面。手改的落点是规格文件——纯本地 HTML 自己写不了文件，所以"在图上直接拖改"要么经 mods，要么退一步做成"在图上点选＋留意见，AI 改规格后重画"，后者更省事，也符合"主要是用户提意见、AI 来改"。
7. **厂商适配**：每家一条命令模板（`claude -p …`、`codex exec …`、`gemini -p …`、`agent -p …`、`goose run …`），统一成"读规格和半成品路径→把产物写到约定路径"；验收只看文件，不依赖退出码。

**需要先拍板的岔路：门和状态谁来执行**
- **路 A：全部放进原生工作流脚本。** 每站是一个 `agent()`，门是"另一个代理去跑检查命令并用 `schema` 报通过与否"，退回是脚本里的循环，状态文件由代理顺手写。好处：零额外程序，白得 `/workflows` 进度视图、暂停、续跑缓存、并发控制。代价：机器门隔着一层模型（多花 token，且判定经过转述）；换厂商要绕 MCP 或让 Claude 代调；人审门要切段；跨会话的进度仍要靠状态文件。
- **路 B：外部薄运行器（一个本地小脚本）逐站调用命令行代理。** 运行器自己读规格、跑检查命令、写状态文件、决定退回；每站用 `claude -p` 或别家的无头命令。好处：机器门是真正的机器判、状态天然在文件、换厂商只换命令模板、人审门自然停住、可无人值守。代价：要自己写并维护这个运行器；失去 `/workflows` 视图和续跑缓存；并行和限流要自己管。
- **折中：** 设计、试跑、改线这些"探索期"的活在对话里用原生工作流做（路 A，快）；线被用户认可、进入反复投料后，由规格文件生成路 B 的运行器来跑（稳、便宜、可换厂商）。规格文件是两条路共用的单一事实来源，所以从 A 换到 B 不需要重新设计线。这与用户"先成熟再上线"的标准一致。

**成本与风险提醒**
- 原生工作流按代理数烧 token；官方的"规模建议"默认每次少于 10 个代理（Pro 少于 5 个）。一条 5 站、每站带一个验门代理、允许退回两次的线，一件活最坏要 20 个以上代理。路 B 的机器门不花 token。
- 订阅额度撞顶时，`claude -p` 里的工作流直接失败而不是暂停——无人值守投料必须靠状态文件支持"从断点接着跑"。
- 官方功能变化快（最新版 2.1.325 发布于 2026-11-13，mods 是 2.1.287 才默认开启的）。薄层越薄、越依赖文件而不依赖某个界面功能，被官方更新冲掉的风险越小。

### Gaps
- 以上"薄层七样"和"两条路"是基于文档的设计推断，**没有任何一项做过原型验证**；尤其是：让工作流代理稳定地按路径读写状态文件、mods 面板在 Windows 版 Desktop 上显示 SVG 的实际效果、本地 HTML 预览里脚本能做到什么程度，都需要动手试。
- 没有比较两条路的真实花费（需要实际跑一条样例线才有数）。
- "手工做成过至少两次才上线"这条前提是否已满足，属于用户项目内部的事实，不在本次调研范围。
- 其他研究者可能覆盖的相邻领域（n8n、Dify、LangGraph 这类非命令行的工作流平台）本笔记没有涉及，"生态里最明显的空档"这一判断只对命令行代理这一圈成立。
